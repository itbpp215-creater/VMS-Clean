# Core Business Logic Invariants
> **⚠️ กฎข้อบังคับ (Non-negotiable Rules)**
> ห้ามแก้ไข เปลี่ยนแปลง หรือลบล้าง Business Logic เหล่านี้ ยกเว้นจะมีการยืนยันและได้รับอนุญาตอย่างเป็นทางการ และทุกครั้งที่มีการแก้โค้ดจะต้องยึดตามหลักการเหล่านี้เสมอ

## 1. Logic ของ AI (Object Detection)
* **การประมวลผล:** รันด้วยโมเดล YOLO11m 640x640 บน ONNX Runtime ผ่าน NVIDIA GPU
* **สิ่งที่ตรวจจับ (Global Anchor):** `person`, `car`, `motorcycle`, `truck`, `bus`
* **ความสัมพันธ์กับ LPR:** ระบบตั้งใจเปิดตรวจจับ `truck` และ `bus` ไว้ด้วย เนื่องจากรถกระบะบางคัน YOLO มองเป็น `truck` หากไม่เปิดไว้ Frigate จะไม่มี Event รถกระบะส่งไปให้ระบบ LPR อ่านป้าย
* **การตั้งค่า:** สามารถปรับแต่งให้กล้องแต่ละตัวตรวจจับ Object อื่นๆ แยกกันได้อย่างอิสระผ่าน Dashboard

## 2. Logic ของ Main/Sub Stream
* **การบันทึกภาพ (Recording):** ระบบจะใช้ **Main Stream** (ความละเอียดสูง) ในการบันทึกวิดีโอลงฮาร์ดดิสก์เสมอ
* **การตรวจจับ AI (Detection):**
  * **กล้องทั่วไป:** จะใช้ภาพจาก **Sub Stream** ในการทำ AI เพื่อลดภาระการประมวลผลของ CPU/GPU
  * **กล้อง LPR:** จะบังคับใช้ **Main Stream** ในการทำ AI ด้วย เพื่อรักษาความคมชัดของป้ายทะเบียนให้มากที่สุด
* **ความปลอดภัย (Credentials):** ใน Stream URL จะไม่มีการใส่ Username/Password ตรงๆ เด็ดขาด แต่จะใช้ตัวแปรแบบ `{FRIGATE_SITE_USER}:{FRIGATE_SITE_PASS}` เพื่อป้องกันรหัสผ่านหลุดเข้าไปในไฟล์ Config

## 3. Logic ของการเปิด-ปิดกล้อง (Camera Toggling)
* **การส่งคำสั่ง:** ทำผ่าน **Config-API** โดยการดึง Draft จาก Dashboard แล้วส่งเข้าไป
* **การทำงานหลังบ้าน:** ระบบจะแก้ไขไฟล์ `config.yml` ให้อัตโนมัติ (`applyEnabledChanges`) เพื่อปรับสถานะ `enabled`, `detect.enabled` และ `record.enabled` โดย `record.enabled` ต้องเป็น `true` เมื่อเปิดกล้อง และ `false` เมื่อปิดกล้อง
* **การปรับ Role กล้อง:** มีกระบวนการ `sync_detect_roles` เพื่อเช็คว่าถ้าสั่งปิด AI (Detect) มันจะลบ `detect` role ของ ffmpeg ออกด้วย **โดยจะเคารพการตัดสินใจของผู้ใช้** (ถ้าผู้ใช้ตั้งใจปิด AI มันจะไม่ถูก auto-override เปิดกลับขึ้นมาเอง)
* **การจบกระบวนการ:** สั่ง Restart Frigate ผ่าน Docker socket เพื่อใช้ Config ใหม่

## 4. Logic ของการเพิ่ม/ลบ/แก้ไขกล้อง
* **ความปลอดภัยของไฟล์:** เมื่อมีการสั่งบันทึกกล้อง ระบบจะทำการล็อคไฟล์ (OS Interprocess Lock) แบบ Transaction ป้องกันปัญหาผู้ดูแลระบบกดเซฟพร้อมกันแล้วไฟล์พัง และมีการสำรองไฟล์ที่ `config/backups/` ทุกครั้ง
* **การทำความสะอาด Stream (Cleanup):** เมื่อมีการแก้ไขชื่อหรือ "ลบ" กล้องทิ้ง ระบบ Config-API จะทำการลบ URL ของกล้องนั้นๆ ทั้ง `main` และ `_sub` ออกจาก `go2rtc` อัตโนมัติ เพื่อไม่ให้เกิดปัญหา Stream ผี (Orphan streams) ตกค้างในระบบ
* **Validation:** ก่อนเริ่มเซฟ Config Validator จะเช็คว่ามี User/Pass ที่ไม่ได้ใช้ Placeholder `{FRIGATE_*}` หรือไม่ หากมีจะ Reject ทันที

## 5. Logic ของการจัดกลุ่มกล้อง (Grouping)
* ข้อมูลการจัดกลุ่ม (Group Metadata) ของแต่ละกล้อง จะถูกบันทึกแยกไว้ที่ไฟล์ `config/nvr_groups.json`
* เมื่อมีการแก้กลุ่มในหน้า Dashboard และกดเซฟ ระบบ Config-API จะทำการล็อคและบันทึกไฟล์ทั้ง `config.yml` และ `nvr_groups.json` ไป **พร้อมๆ กัน (Atomic Commit)** ถ้าระบบพังกลางคัน ค่าทั้งหมดจะ Rollback กลับอัตโนมัติ

## 6. Logic ของการเชื่อมต่อกองร้อยอื่น (Watchlist Federation)
* **แหล่งข้อมูล:** ระบบจะอ่านรายชื่อ IP/โหนด ของกองร้อยอื่นที่ได้รับอนุญาตจากไฟล์ `/dashboard-settings/nodes.json`
* **กระบวนการซิงค์:** ทุกครั้งที่รีโหลด ระบบจะยิง API ไปขอดูข้อมูลบัญชีเฝ้าระวังของโหนดอื่นผ่านทาง HTTPS (ถูกล็อคด้วย VPN CIDR และต้องมี `WATCHLIST_FEDERATION_SHARED_SECRET`)
* **การรวมข้อมูล (Merge):** ระบบจะรับป้ายเฝ้าระวังจากกองร้อยอื่นมาใส่ในระบบตัวเอง **เฉพาะในกรณีที่ป้ายนั้นยังไม่มีในฐานข้อมูลของตัวเอง** เท่านั้น
* **การปกปิดข้อมูล:** ข้อมูลที่ซิงค์กันจะมีแค่เลขป้ายและระดับความเสี่ยง จะ**ไม่มีการส่งข้อมูลส่วนบุคคล** (ชื่อเจ้าของ/เบอร์ติดต่อ) ข้ามเครือข่าย เพื่อความปลอดภัยของข้อมูล

## 7. Logic ของการตรวจจับทะเบียน (LPR)
* **การทำงาน:** เป็นโปรแกรมที่แยกตัวออกมา (Sidecar) ไม่ได้ดึงภาพจากกล้องเองตรงๆ แต่รอจังหวะ **Event-driven**
* **Trigger:** จะทำงานก็ต่อเมื่อ Frigate แจ้งเตือนว่ามีรถเข้ามา (Vehicle Event)
* **Zone Trigger:** เมื่อกล่อง AI ของรถ (Bounding Box) ลากไปสัมผัสหรือเข้าไปในเขต "LPR Zone" ที่ผู้ใช้ตีกรอบไว้ ระบบถึงจะดึงภาพความละเอียดสูง ณ เสี้ยววินาทีนั้นมา
* **OCR Reading:** ส่งเข้าโมเดล `license_plate.pt` (หาป้าย) และ `data_plate.pt` (อ่านอักษรไทย)
* **Mainstream Multi-frame:** เมื่อกล้องมี vehicle event เดียว ระบบจะสุ่มภาพ main feed แบบมีเพดาน ให้คะแนนขนาด/ความคม/ความมั่นใจ และต้องอ่านตรงกันข้ามเฟรมก่อนเผยแพร่ผล AI; หากมีหลาย event พร้อมกันจะใช้ snapshot กับกรอบ event เพื่อไม่ผูกป้ายผิดรถ
* **AI Pending Result:** ผลที่อ่านได้ครบและผ่าน multi-frame consensus จะเขียน `recognized_license_plate`/`sub_label` ให้ Frigate แสดงในหมวดป้ายทะเบียนทันที แต่ยังคงสถานะรอตรวจสอบ
* **Human Truth:** partial/unreadable ไม่สร้างข้อความทะเบียนปลอม ผู้ดูแลยืนยัน/แก้ไข/ปฏิเสธได้ และคำตอบมนุษย์จะเขียนทับหรือล้างผล AI
* **การแจ้งเตือน (Alerts):** Watchlist history และ Discord/Telegram alert เกิดหลัง human confirmation เท่านั้น เพื่อไม่ให้ผล AI ที่ยังไม่ตรวจสร้างเหตุแจ้งเตือนผิด
